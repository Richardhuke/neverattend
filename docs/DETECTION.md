# 学校端能看到什么、以及怎么少留痕

本文只讨论「浙大体艺 App 的签到请求到达服务端后，服务端与老师侧可能观察到什么」，以及在这个前提下
我们这套东西（网页排队 → 执行机 adb 驱动 → 系统测试 provider 注入坐标）还能怎么收敛特征。

结论先说：**这不是"能不能被发现"的问题，而是"留下多少可复核痕迹"的问题。**
系统层面（Android `Location.isFromMockProvider()`）**一定**能给服务端一个"这是模拟位置"的布尔值；
服务端存不存、看不看、事后查不查，我们看不到。所以策略只能是：把能控的特征都控住，把不能控的风险讲明白。

---

## 一、服务端一定拿得到的东西

签到请求（WebView 里的 H5 页面发的那个 POST）通常带这些字段，或能从会话/请求头推导出来：

| 类别 | 具体内容 | 我们能控吗 |
| --- | --- | --- |
| 账号 | 学号、姓名、学院、班级、课程 ID、课次 ID | 不可控，就是本人 |
| 时间 | 服务端时间戳、客户端上报时间 | 部分可控（见下） |
| 位置 | 经纬度、精度半径 accuracy、坐标系（GCJ-02 / WGS84） | 可控（注入值） |
| 位置来源 | `isFromMockProvider` / `Location.isMock` 布尔 | **不可控**（系统测试 provider 也是 mock） |
| 设备 | 设备型号、系统版本、App 版本号、IMEI/OAID/AndroidID（若采集） | 可控（真机就是真值） |
| 网络 | 出口 IP、运营商、是否代理/VPN | 可控（用手机流量，别挂代理） |
| 会话 | JWT / Cookie、请求签名（`cgAuthorization`） | 不可控，App 原生生成 |

老师侧（管理端）通常还能看到：**签到方式**（GPS / 手动 / 扫码）、**签到时间点**、**签到位置**、
以及一条「异常/待认证」的标记位。实测你这门课的记录里就是「GPS 2026-11-05 17:00:17 → 到」这种粒度。

## 二、真正容易露的六件事（按危险度排序）

1. **`isFromMockProvider = true`**
   最硬的一条。系统测试 provider（`cmd location providers add-test-provider gps`）注入的位置，
   Android 会打上 mock 标记，App 侧一行代码就能读出来。第三方 Fake GPS 走「模拟位置应用」通道同样带标记。
   → 我们无法消除。只能靠「服务端目前看来只判距离、不判 mock」这个**观察**（第 8 次课实测才能确认）。

2. **位置精度与抖动不自然**
   真人 GPS 在田径场会有 3–15 m 的随机漂移、accuracy 在 5–30 m 之间跳。
   如果我们每次都写死 `accuracy=5`、坐标一模一样、两次签到相距 0 米 → 极不自然。
   → 已处理：`deploy/adb-ns.mjs` 的 `setMockLocation()` 每次注入前做极坐标抖动（`NA_JITTER`，默认 8 m 半径，
   实测 2000 次采样落在 0.14–8.00 m），accuracy 默认在 6–18 m 随机（`NA_MOCK_ACC` 可固定）。

3. **移动速度不合物理**
   上一次签到在宿舍（或另一个城市），这一次在田径场，中间隔 3 分钟 → 时速几百公里。
   → 已处理：一个账号固定一台设备、固定圈内坐标，不做跨城瞬移。

4. **签到时刻太"机器"**
   开课 17:10，真人 17:09:41 / 17:14:11 / 17:00:17 都有；如果我们每次都在整点后固定 0 秒、
   或每次都在开窗第一毫秒提交 → 一眼脚本。
   → 已处理：驱动支持 `NA_DELAY_MAX=<秒>` 在点按钮前随机等待（默认 0，由 worker 的 claim 时刻决定）；
   网页排队时也可以自己在合适的时间点提交，而不是固定在开窗瞬间。

5. **同 IP 多账号并发**
   一台机器/一个出口 IP 上十分钟内出现 30 个学号 → 最容易被判定为代签农场。
   → 已处理：worker 串行执行、单账号单设备；不做批量代签。

6. **失败就重试、反复点圆钮**
   服务端日志里同一个课次出现 5 次请求 → 明显异常。
   → 已处理：`failsafe`，一旦被拒（"未发现考勤地点""不在范围"）立刻停手，不刷。

## 三、这套系统的取舍（写给自己看的诚实结论）

- **网页排队这一层是安全的**：学校看不到我们的网站，只看到 App 发出去的请求。
- **执行机（本机 + 一台真机）是唯一能被指纹识别的环节**，而它的指纹 = 你这台手机的真实指纹。
  也就是说：**只要一台设备只登一个账号，学校侧看到的就是"某人用自己的手机在操场签到"**。
- **唯一的破绽是 mock 标记**。如果服务端哪天开始记这个字段，所有走模拟定位的方案（包括花钱买的 Fake GPS）一起失效。
- **模拟器农场不可行也不划算**：模拟器的机型/传感器/GPU 指纹和真机差得远，反而比 mock 标记更容易被抓；
  而且我们现在的服务器（阿里云 2C2G Windows）根本跑不了嵌套虚拟化。

## 四、今天（11-12 第 8 次课）的实操口径

1. 17:05 插线，`node deploy/device-worker.mjs --serial 10AG1H0QJE004HC` 起执行机。
2. 网页上填学号 + 坐标（老师发布考勤范围后按圈心改），点「排队签到」。
3. 观察三件事，按结果决定后续：
   - 成功 → 说明服务端不校验 mock，方案可用；
   - 提示"不在范围" → 坐标偏了，按考勤圈心微调；
   - 提示"位置异常/无效" → 服务端校验 mock，**这条路到此为止**，只能人真去。
4. 签退同理，17:50 之后再点一次「排队签退」。

> 一句话：能控的都控了，剩下的是服务端要不要查。今天这一次实验就是为了把这个问题问清楚。
